# Full-Stack QA Audit & Scoring — Student Academic OS

**Date:** 2026-08-07
**Method:** Direct evidence — full source reads, live `npm run build`, live `vitest run`, repo/config inspection. Supersedes the partial `FULL-STACK-AUDIT.md` (08-05); items fixed since then are noted.

**Architecture in one line:** React 18 + Vite + TypeScript **offline-first PWA** (Dexie/IndexedDB), thin Supabase PostgreSQL backend reached only via SECURITY DEFINER RPCs (anon key + RLS). **No custom server.**

---

## 1. Frontend — 7/10

**Implemented:**
- Clean layer split: `src/features` (16 views), `src/components/ui` (12 shared primitives), `src/lib`, `src/store`, `src/db`. Refactored onto a shared UI kit documented in `DESIGN_SYSTEM.md`.
- Single `ErrorBoundary` wraps the whole app with a reset button (`src/components/ErrorBoundary.tsx`); seed-failure screen with Retry (`src/app/App.tsx:54-67`).
- `BottomSheet` now ships `role="dialog"`, `aria-modal="true"`, and an **Escape-to-close** handler (`BottomSheet.tsx:19-21,33`) — two prior-audit a11y gaps fixed.
- **55/55 unit tests pass** (5 files: adminKeys 25, adminMigration 11, accessKeyMigration 8, attendanceMath 7, accessKeys 4).
- TS strict, zero `@ts-ignore`. PWA manifest + PNG icons present (prior "missing icons" gap fixed).
- Empty states on every view.

**Missing / weak:**
- **No per-view error boundaries** — one crash in any subview kills the whole app (`App.tsx:89` wraps everything).
- **No code-splitting** — single 682.22 kB JS chunk (185.49 kB gzip); Vite itself warns "chunks larger than 500 kB". All 16 subviews eagerly imported.
- **No focus trap / auto-focus** in bottom sheets (still open, despite Escape + aria-modal now being fixed).
- **Icon-only back buttons lack `aria-label`** (e.g. `AdminPortalView.tsx:164,181,214`), plus edit/delete icon buttons in lists.
- `viewport` has `user-scalable=no` (`index.html:5`) — WCAG 1.4.4 violation (pinch-to-zoom blocked).
- No `<h1>` on views; no `aria-live` for status messages; no component-level tests (logic-only coverage).
- Many IndexedDB writes are bare `await` without try/catch (unhandled-rejection risk).

## 2. Backend / APIs — 7/10

**Implemented:**
- 6 SECURITY DEFINER RPCs, every one `set search_path = public`, every one self-authorizes via `p_admin_code` and returns `{ok, error}` JSON (`0002_admin_portal.sql`).
- Input validation: role whitelist + owner-only gating, `max_uses` clamped to [1,100], codes normalized uppercase/trim.
- Atomic last-use consumption (`0001_access_keys.sql:70-77`), 3-attempt code-collision retry.
- Machine error codes → human messages everywhere in the UI.

**Missing / weak:**
- ~~No rate limiting or lockout anywhere~~ — **Resolved 2026-08-07.** `activate_access_key` now counts failed attempts per key and locks for 15 minutes after 5 failures (`0003_rate_limiting.sql`). Residual: `INVALID_KEY` (wrong guess, no key matched) is not per-key countable; the 32^16 code space makes random guessing infeasible.
- No expiry validation on `admin_generate_key` (a past date mints an already-expired key).
- Client RPC calls have no timeout/retry/backoff (`adminKeys.ts:161-174`).

## 3. Database — 8/10

**Implemented:**
- Minimal, correct schema: `access_keys` + `profiles`, both **RLS-enabled with zero anon policies** and `revoke all` from anon/authenticated (`0001_access_keys.sql:106-113`). Only definer functions can touch the data.
- Unique constraint on `code`; FK + unique on `profiles.access_key_id`; deterministic `created_by` audit column on keys.
- Numbered, idempotent migrations (`create if not exists` / `create or replace`); no destructive ops; no seed secrets in migrations.

**Missing / weak:**
- `access_keys_code_idx` (`0001_access_keys.sql:26`) is redundant — the `UNIQUE` constraint already creates that index.
- No action-audit table (who deactivated what, when). `created_by` exists but no event log.
- No DB-level backup automation in the repo (relies on the Supabase platform tier).

## 4. Servers — N/A

There is no application server. The app is a static `vite build` output; all backend is managed Supabase. This is a deliberate and sound architecture for an offline-first PWA — nothing to score.

## 5. Networking — 6/10

**Implemented:**
- HTTPS end-to-end (Supabase REST is TLS; deployed frontend would be too).
- Tiny external surface: one Supabase host + Google Fonts.
- CORS irrelevant to the app itself (only `supabase.rpc` calls; browser-to-Supabase, same origin story).

**Missing / weak:**
- No **Content-Security-Policy** (no meta tag, no server headers — would live at the deployment layer).
- No verifiable CORS **origin allow-list** on the Supabase project (dashboard-managed; default is permissive — acceptable for a public PWA with anon-key auth, but unverified).
- No rate limiting at the network boundary (edge/CDN layer) — the per-key lockout in `0003` covers the app layer (see #2).

## 6. Cloud Infrastructure — 3/10

**Implemented:**
- One managed Supabase project; anon key + RLS is the correct security model.
- Env hygiene is good: `.env.local` gitignored, `.env.example` documents the two vars, and only the public **anon** key is in the client (`supabase.ts`).

**Missing / weak:**
- **The app is not deployed anywhere.** No Netlify/Vercel/Pages/gh-pages config exists, and there is no live URL. Students currently have no way to run it — the "send students this link" step in ADMIN_GUIDE.md is a placeholder. This is the most important infra gap.
- No staging/production separation (one Supabase project serves dev and would serve live).
- Repo remote is named `COMPANION` (github.com/vishvrajsolanki-dev/COMPANION) — cosmetic mismatch with the app name.

## 7. CI/CD — 1/10

**Implemented:** Nothing. No `.github/workflows`, no lint gate, no test gate, no deploy pipeline. Build + tests are manual (`npm run build` / `npm test`).

**Missing / weak:** Everything — a push-triggered `test` + `build` job, and a deploy-on-merge job, would cover the whole gap.

## 8. Security — 7/10

**Implemented (all verified):**
- Role-gated access keys; owner-only admin/owner minting; admin cannot deactivate the owner key nor their own key.
- RLS fully locked down; definer RPCs are the only ingress.
- Privileged codes masked (`ACAD-****-****-1A2B`) for non-owner callers; owner sees all.
- Atomic consumption prevents key overselling; anon-only credentials in the client.

**Missing / weak:**
- ~~No rate limiting / lockout~~ — per-key lockout shipped in `0003` (activation brute-force).
- ~~**Owner key committed in plaintext**~~ — **Resolved 2026-08-07.** The original owner key was rotated (old key deactivated) and purged from source/docs; all scripts now read `VERIFY_OWNER_KEY` from gitignored `.env.local` via `scripts/lib/env.cjs`. No owner credential remains in the working tree.
- No CSP.
- Deactivating a key does **not** revoke an already-activated device (by design, offline-first). Residual risk is low (student data is all local) but "deactivate" ≠ "kick out".
- Admin/owner raw key persists in `localStorage` as the RPC credential — an XSS vector would exfiltrate it; no CSP partially mitigates.

## 9. Containers — N/A

Static PWA + managed Postgres. A Dockerfile would add nothing and lose the zero-ops benefit. Correctly absent.

## 10. CDN — 5/10

**Implemented:**
- Service worker precaches all app-shell assets (10 entries, ~707 kB) and caches Google Fonts CacheFirst 1y (`vite.config.ts:33-50`).
- Vite content-hashed filenames give cache-busting.

**Missing / weak:**
- No actual edge/CDN network because nothing is deployed. Once hosted on Vercel/Netlify/Cloudflare Pages, edge delivery is automatic. Score reflects "SW works, edge doesn't exist yet."

## 11. Monitoring & Logging — 2/10

**Implemented:** `console.error` in `ErrorBoundary` and on RPC failures; nothing else.

**Missing / weak:** No error tracker (Sentry/LogRocket), no analytics, no performance/Core Web Vitals capture, no structured log store. Acceptable for a personal tool, but zero visibility into a live deployment that students depend on.

## 12. Backups & Recovery — 7/10

**Implemented (verified current):**
- Full JSON backup export of every Dexie table (`ProfileView.tsx:35-53`).
- **Restore from JSON** in an atomic clear+insert transaction (`ProfileView.tsx:56-90`) — prior "backup is one-way" gap is **fixed**.
- Wipe-all requires typing `DELETE`, auto-exports a backup first, and skips re-seeding afterwards.
- Server-side data (keys/profiles) is protected by Supabase's platform-managed backups (plan-tier dependent, not in repo).

**Missing / weak:**
- Backup is manual-only; no scheduled/auto-backup and no reminder.
- No way to restore *server-side* key state (e.g. a deleted key) from the app — only via Supabase dashboard.

## Biggest Risk

**A public activation endpoint with nothing deployed in front of it.** The anon key is public by design; `activate_access_key` is now protected server-side by a per-key lockout (`0003`, 5 failures → 15-minute lock), but the frontend has no production host, so the access-key system has no live surface yet. The bigger issue now is the missing deploy: build the door before the lock matters.

## Top 5 Prioritized Actions

1. **Deploy + wire CI/CD (unblocks everything).** Host the static build on Netlify/Vercel/Cloudflare Pages, add a push workflow running `tsc + vitest + vite build`, and deploy on merge. Gives students a URL, adds HTTPS/edge/CDN, and lets ADMIN_GUIDE's link be real. *(Closes #6, #7, #10 in one move.)*
2. ~~**Throttle activation abuse server-side.**~~ **Done 2026-08-07** — `0003_rate_limiting.sql` adds `failed_attempts`/`locked_until` to `access_keys`; 5 failures locks a key for 15 minutes (`TOO_MANY_ATTEMPTS`). *(Closed the #2/#8 brute-force gap.)*
3. **Fix the a11y high-priority items.** Focus-trap + auto-focus in `BottomSheet`, `aria-label` on icon-only buttons (16+ sites), drop `user-scalable=no`. *(#1.)*
4. **Resiliency: per-subview error boundaries + guarded DB writes.** One `ErrorBoundary` per subview so a crash doesn't kill the app; wrap IndexedDB mutations in try/catch with user-facing banners. *(#1.)*
5. **Monitoring + backup automation.** Add error tracking (Sentry or a light self-hosted beacon) and a scheduled backup reminder. *(#11, #12.)* *(Key hygiene — rotation + env-only storage — was completed 2026-08-07, closing #8.)*
